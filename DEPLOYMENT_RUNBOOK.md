# Manual deployment runbook — gnoland (sentry / validator / tmkms)

Ansible no longer deploys the gnoland nodes themselves: only the server
foundation (`base_setup.yml`) is automated. The files specific to each
deployment (`entrypoint.sh`, `config.toml`, `genesis.json`) change with every
gno version (build, genesis, download links) — pushing them by hand instead
of maintaining an automation that would need updating on every release
avoids a false sense of safety and keeps deployment explicit.

This document is the reference runbook. No automation here: just commands to
run, in order, on the right hosts.

## 0. Prerequisites

1. `base_setup.yml` already ran on each host (sentry, validator):
   ```bash
   ansible-playbook -i inventory.yaml base_setup.yml -e target=gno-sentry
   ansible-playbook -i inventory.yaml base_setup.yml -e target=gno-validator
   ```
2. Pick a topology among the four available under `compose/`:
   - `compose/sentry-alone/` — sentry only.
   - `compose/validator-alone/` — validator only + otel-collector.
   - `compose/validator-sentry-tmkms/` — sentry + validator + tmkms sidecar
     (softsign) on the same host.
   - `compose/tmkms-alone/` — dedicated tmkms signer host (TCP mode, paired
     with `compose/validator-alone/` on the validator host — see `TMKMS.md` §4).

## 1. gnoland secrets — never generated by Ansible

On **every** gnoland node (sentry and/or validator), do this manually, once:

```bash
ssh root@<node-ip>
mkdir -p /root/<gno_dir>          # e.g. /root/gnoland1
cd /root/<gno_dir>
# For validator-sentry-tmkms, do this separately in ./sentry/ and ./validator/
gnoland secrets init
gnoland secrets get                # note node_id, p2p_address, validator_address
```

Note the `node_id`/P2P addresses needed to build the other nodes'
`PERSISTENT_PEERS`/`PRIVATE_PEER_IDS`. Also get `SEEDS` from the network
operator (gnocore or equivalent).

## 2. Non-secret files — partially automated, partially manual

For each gnoland node (flat layout for `sentry-alone` and `validator-alone`;
`sentry/` and `validator/` subdirectories for `validator-sentry-tmkms`):

| File | Source | How it gets there |
|---|---|---|
| `docker-compose.yml`, `.env.example` | `compose/<compose_target>/` in this repo | `deploy-compose.yml` (Ansible) |
| `entrypoint.sh` | `validator/entrypoint.sh` in this repo | `deploy-compose.yml` (Ansible) |
| `check_status.sh` | `validator/check_status.sh` in this repo | `deploy-compose.yml` (Ansible) |
| `otel/otel-config.yaml` | `validator/otel/otel-config.yaml` in this repo (only when the topology has an otel-collector) | `deploy-compose.yml` (Ansible) |
| `config.toml` | provided by the network (gno.land deployment URL for the target chain) | manual, always |
| `genesis.json` | provided by the network (genesis URL for the target chain) | manual, always |
| `.env` | copied from the pushed `.env.example`, then filled in | manual, always — `deploy-compose.yml` never touches `.env` |

`deploy-compose.yml` only pushes the four **stable** files above — the ones
maintained in this repo and identical across deployments of the same
topology. It deliberately never touches `.env`, `config.toml`,
`genesis.json`, or any secret: those change with every gno version/network
and stay a fully manual step (see §0's rationale).

```bash
ansible-playbook -i inventory.yaml deploy-compose.yml \
  -e target=gno-sentry -e compose_target=sentry-alone
```

Then, still by hand, on the host:

```bash
ssh root@<sentry-ip>
cd /root/gnoland1
curl -fsSL <config_url> -o config.toml
curl -fsSL <genesis_url> -o genesis.json
```

`compose_target` is one of `sentry-alone`, `validator-alone`,
`validator-sentry-tmkms` (matching the `compose/` directories) — see
`deploy-compose.yml`'s header for the exact usage per topology. It creates
the right layout on its own (flat, or nested `sentry/`+`validator/` for
`validator-sentry-tmkms`) and copies `otel/otel-config.yaml` only when the
topology has an otel-collector.

For `tmkms-alone` (dedicated signer host), there is no gnoland node at all —
`deploy-compose.yml` does not apply to it (its `assert` rejects that target);
see §4 instead. Note that `setup-tmkms.yml` stages `tmkms.toml`, the
Dockerfile, `secrets/` and the kms-identity key, but **not**
`compose/tmkms-alone/docker-compose.yml` — copy that one by hand into the
same directory as the rendered `tmkms.toml`:

```bash
scp compose/tmkms-alone/docker-compose.yml \
  root@<signer-host>:/root/<gno_dir>/tmkms/
```

## 3. `.env` and startup

On the host, in the chosen compose's directory:

```bash
cp .env.example .env && chmod 600 .env
# fill in IMAGES, MONIKER(_*), SEEDS, PERSISTENT_PEERS(_*), PRIVATE_PEER_IDS, TMKMS_CHAIN_ID...
docker compose pull
docker compose up -d
```

Validate:

```bash
bash check_status.sh .        # or the node directory's path
docker compose logs -f
```

## 4. tmkms — same-host sidecar or dedicated signer host

**Same-host (`validator-sentry-tmkms`, uds mode):** the tmkms sidecar
(image, `tmkms.toml`, resliced signing key) is prepared by Ansible, **after**
step 1 (the validator's gnoland secrets must already exist) and **before**
the `docker compose up -d` from step 3:

```bash
ansible-playbook -i inventory.yaml setup-tmkms.yml \
  -e target=gno-validator -e tmkms_chain_id=<chain-id>
```

**Dedicated signer host (`tmkms-alone` + `validator-alone`, tcp mode):** the
role runs on the signer host instead, and needs the validator's peer-id and
IP, plus the consensus key resliced on the validator host and copied over —
see `TMKMS.md` §4 for the full step-by-step:

```bash
ansible-playbook -i inventory.yaml setup-tmkms.yml \
  -e target=<signer-host> -e tmkms_connection_mode=tcp \
  -e tmkms_chain_id=<chain-id> \
  -e tmkms_validator_peer_id=<hex> -e tmkms_validator_ip=<validator-ip>
```

In both modes, this playbook fails explicitly (never generating a secret) if
the required key material isn't in place yet — go back to step 1 (or the
manual reslice+copy step in tcp mode) in that case. See
`roles/tmkms/README.md` for the full internals (reslice, kms-identity key
generation/derivation).

## 5. Updating a chain (new gno version / new network)

1. Stop the node: `docker compose down` (or just the relevant service).
2. Replace `entrypoint.sh`/`config.toml`/`genesis.json` with the new versions
   (step 2 above), update `IMAGES` in `.env`.
3. Depending on the nature of the change (chain reset vs. compatible
   upgrade), clear `gnoland-data/` or not — **never touch**
   `gnoland-data/secrets/` (or `tmkms/secrets/` in tmkms mode) without a
   deliberate backup/key-rotation policy.
   **New network / new `chain_id` with tmkms** (typically: this directory
   was copied from the previous testnet): follow `TMKMS.md` §10 — the stale
   `consensus_state.json` and the three `chain_id` occurrences in
   `tmkms.toml` must be dealt with, or the validator silently never signs.
4. `docker compose pull && docker compose up -d`, then `check_status.sh`.

## 6. Logs and metrics

Nothing to do here beyond `base_setup.yml`: the `alloy` role (already
included) scrapes `node_exporter`/`otel-collector` locally and pushes the
gnoland containers' Docker logs via remote_write/push. See
`NETWORK_AND_REVERSE_PROXY.md` for the relay mode through the sentry if the
validator is isolated on a private VLAN.

## 7. Cold log retention (optional, independent of Alloy)

`backup-logs.yaml` stays active and independent from this runbook: it
deploys `backup.sh` (validator, 24h extraction + SCP to the sentry) and
`rotate.sh` (sentry, 30-day retention), in addition to the Alloy pipeline —
useful as cold retention beyond the logs backend's own retention window.

```bash
ansible-playbook -i inventory.yaml backup-logs.yaml
```
